# Patching a GBA ROM safely

"Patch" here means editing the game's bytes, data or code, so it loads your modified content. The goal is a ROM that
still boots, still plays every other level, and can be distributed as a diff rather than as copyrighted data.

## Contents
1. Decide: data edit, pointer redirect, or code hook
2. Free space
3. Code hooks in Thumb, with an ARM body (the klo-gba.js loader patch, annotated)
4. Hand-assembling: encodings you need and PC-relative rules
5. Marking a patched ROM and verifying it
6. Distributing patches, not ROMs

## 1. Decide the least invasive edit

1. **Data edit in place.** New blob is no bigger than the old one: overwrite it, pad with zeros. Cheapest, no code change.
   Fails silently when the blob grows: it overwrites the next asset (Klonoa Part 7: level N worked, level N+1 crashed).
2. **Pointer redirect.** Put the new blob in free space and change the table entry that pointed at the old one
   (`gba_rom.py pointers rom.gba <old>` finds it). Works when the address is read from a table.
3. **Code hook.** The address is computed or the table is shared by logic you cannot change in place. Insert a branch
   to your own code in free space, do the extra work there, re-execute what you displaced, return. This is what
   klo-gba.js does, because Klonoa's loader derives the tilemap address in code.

## 2. Free space

Cartridges are padded to a power-of-two size, so the tail of the ROM is usually a long run of `0xFF` (or `0x00`).
`gba_rom.py freespace rom.gba --min 0x1000` lists runs; the one flagged `end of ROM` is the safe choice. Reserve a
layout up front (e.g. code stub at the start, a table after it, then assets at fixed slots per level as klo-gba.js
does: `0x367700`, `0x3686B0`, ...) so re-saving a level is idempotent. Never assume interior zero runs are free; they
may be real data. If the ROM is full, it can be grown to the next power of two (the header has no size field), but
some flash carts and emulators care about the size, so prefer the existing padding.

## 3. Code hooks

Anatomy of the Klonoa custom-level loader (file offsets; bus = +0x08000000), generated by `scissors/src/rom.js`:

```
043B0C   23 F3 80 FD        bl 0x08367610            ; hook: replaces one 32-bit instruction pair in the loader
                                                     ; (originally `mov r4, r1` + the next halfword)
367610   78 46              mov r0, pc               ; Thumb stub in free space: pc reads 0x08367614
367612   3C 30              add r0, #0x3C            ; r0 = 0x08367650, the ARM body (word aligned, bit0 = 0)
367614   00 47              bx r0                    ; switch to ARM state
367620   <orig0><cust0><orig1><cust1>...             ; table: original tilemap address, custom tilemap address (8 bytes/level)
367650   04 00 85 E2        add r0, r5, #4           ; recompute the value the loader had in r0 (tilemap address)
367654   3C 40 1F E5        ldr r4, [pc, #-0x3C]     ; r4 = table[i].original   (pc = 0x0836765C, so 0x08367620)
367658   04 00 50 E1        cmp r0, r4
36765C   40 00 1F 05        ldreq r0, [pc, #-0x40]   ; if equal: r0 = table[i].custom (0x08367624)
         ... one 12-byte compare block per level that has a custom tilemap ...
3676xx   01 40 A0 E1        mov r4, r1               ; re-execute the instruction the bl displaced
3676xx   1E FF 2F E1        bx lr                    ; back to Thumb code after the hook (lr has bit 0 set)
```

Design rules the patch illustrates:

- **Hook with `bl`** (4 bytes in Thumb) at a point where `lr` is dead or already saved, and where the displaced
  instruction(s) have no pc-relative dependency (a displaced `ldr rN,[pc,#x]` or a branch cannot be re-executed
  elsewhere as-is; move the hook or recompute the value).
- **Re-execute what you displaced** at the end of the body, then `bx lr`. Returning with `bx lr` lands back in Thumb
  because `bl` set bit 0 of `lr`.
- **Do the work in ARM** if you need pc-relative loads over a table or more registers; the 3-instruction stub
  (`mov r0,pc / add r0,#n / bx r0`) is the standard Thumb→ARM trampoline. Note it clobbers r0, which was fine here
  because the body recomputes r0 (`add r0, r5, #4`) from a register the loader still held.
- **Keep the original data untouched** and only redirect when a custom version exists, so unpatched levels behave
  exactly as before and the same patch can be re-applied.
- **Generate the patch programmatically** (the JS emits bytes per level) so it stays consistent as levels are added.

`scripts/thumb_patch.py hook <site> <stub> --arm-body <addr>` prints all the bytes for steps 1-3 of this recipe.

## 4. Hand-assembling

You rarely need more than a dozen encodings. `thumb_patch.py` computes the address-dependent ones and its self-test
checks them against the bytes above.

| Instruction | Encoding | Notes |
|---|---|---|
| Thumb `bl target` | `F000|((off>>12)&0x7FF)`, `F800|((off>>1)&0x7FF)` | `off = target - (pc+4)`, ±4 MB. Stored little-endian halfword by halfword: `23 F3 80 FD` is `F323 FD80`. |
| Thumb `b target` | `E000|((off>>1)&0x7FF)` | ±2 KB only |
| Thumb `bx rN` | `4700|(N<<3)` | `bx r0` = `00 47` |
| Thumb `mov r0, pc` | `4678` | hi-register mov; pc reads insn+4 |
| Thumb `add rd, #imm8` | `3000|(rd<<8)|imm` | |
| Thumb `ldr rd, [pc, #imm]` | `4800|(rd<<8)|(imm>>2)` | base `(insn+4)&~3`, forward only, ≤1020 |
| Thumb `nop` | `46C0` (`mov r8,r8`) | |
| Thumb `push {lr}` / `pop {pc}` | `B500` / `BD00` | add low regs as bits 0-7 |
| ARM `ldr rd, [pc, #±imm12]` | `E51F d000 | imm` (minus) / `E59F d000 | imm` (plus) | pc reads insn+8; `cond` in top nibble (E always, 0 eq, 1 ne) |
| ARM `cmp r0, r4` | `E1500004` | |
| ARM `add r0, r5, #4` | `E2850004` | |
| ARM `mov r4, r1` | `E1A04001` | |
| ARM `bx lr` | `E12FFF1E` | |
| ARM `b target` | `EA000000 | ((target-(pc+8))>>2)&0xFFFFFF` | |

ARM instructions are 4-byte little-endian words; Thumb are 2-byte little-endian halfwords. ARM code must start on a
4-byte boundary, Thumb on 2. If `arm-none-eabi-as`/`objdump` (devkitARM) is installed, assemble a `.s` file instead and
copy the bytes; the table is for when it is not.

## 5. Marking and verifying

- Stamp the ROM so tools can recognise it: klo-gba.js writes a harmless known instruction (`add r0, #0x42`) at a fixed free
  address and checks for it before deciding whether the region is "custom" or a pristine dump (identified by SHA-1).
- The header checksum at `0xBD` only covers `0xA0-0xBC`; code/data edits do not invalidate it. Some games checksum
  themselves (anti-piracy); if a patched ROM misbehaves everywhere, look for a routine summing the ROM at boot.
- Test in an emulator with the debugger open: put an execution breakpoint on the stub to confirm the hook fires, then
  play the modified level and the levels before/after it.
- Validate round trips: decompress → recompress → decompress must be byte-identical to the first decode.

## 6. Distribute patches, not ROMs

Ship an IPS/BPS/xdelta patch or an editor that takes the user's own dump (klo-gba.js runs entirely in the browser on a
user-supplied ROM and never hosts one). Say which dump (region + SHA-1) the patch expects.
